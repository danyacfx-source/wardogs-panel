# Безопасность и модель угроз

Цель проекта — максимально затруднить получение персональных идентификаторов и административных секретов при краже файла базы или бэкапа. Ни один обычный бот не может гарантировать секретность при полном root-доступе к работающему хосту: процессу нужны ключи в памяти, чтобы работать. Ниже явно указано, что защищено и что остаётся риском.

## Защищённые данные

В SQLite шифруются AES-256-GCM с уникальным nonce и контекстной AAD:

- Discord ID;
- SteamID64;
- отображаемый ник;
- баланс, суммарное и недельное время;
- состояния/сроки VIP;
- реестр постоянных Reserved slots и время установки защиты;
- детали покупок, аудита и начислений;
- ID сообщений и служебные состояния.

Для поиска пользователя используются HMAC blind indexes. Без `DATA_ENCRYPTION_KEY` из украденной БД нельзя напрямую получить исходные Discord/Steam ID, ники или суммы. Видимыми остаются структура схемы, количество строк и временные метки части технических событий.

## Целостность баллов

- Каждое начисление и списание попадает в отдельный HMAC-связанный журнал.
- Баланс пользователя при старте сверяется с суммой журнала.
- Аудит административных операций также связан HMAC-цепочкой.
- При несовпадении бот прекращает запуск, а не продолжает работу с подозрительными данными.
- Ежедневный digest цепочек можно отправлять в отдельный Discord audit channel. Это помогает обнаружить откат локальной БД.

Одна локальная HMAC-цепочка не является абсолютной защитой от полного отката всей БД на старую согласованную копию. Для обнаружения такого сценария бот отправляет ежедневные audit digests в закрытый Discord-канал `1552402077068820611`, а зашифрованные бэкапы — в `1552401803184701502`.

## Секреты

Пять секретов должны быть независимы:

1. `DISCORD_BOT_TOKEN` — полный контроль над ботом; это штатное имя переменной BotHost для Discord.
2. `WARDOGS_RCON_PASSWORD` — административный доступ к игровому API.
3. `WARDOGS_RCON_2_PASSWORD` — административный доступ ко второму игровому API.
4. `DATA_ENCRYPTION_KEY` — чтение рабочей БД и проверка HMAC.
5. `BACKUP_ENCRYPTION_KEY` — расшифровка `.wdsbak`.

На BotHost секреты задаются только через защищённые переменные окружения панели и не входят в образ, ZIP или `.env`. Ключ данных и ключ бэкапов не могут совпадать — бот откажется запускаться. Полный администратор хостинга технически может получить переменные или память процесса, поэтому ключ бэкапов нужно дополнительно хранить офлайн.

Никогда не:

- публикуйте `.env` или каталог `secrets`;
- вставляйте секреты в issue, Discord, скриншот или команду запуска;
- используйте один пароль для Discord, RCON и шифрования;
- храните единственную копию backup key на сервере вместе с бэкапами;
- включайте debug-лог без необходимости.

## RCON

Клиент RCON:

- каждый из двух клиентов подключается только к своему URL из конфигурации;
- не следует redirect;
- разрешает только фиксированный набор WDRCON routes;
- ограничивает время и размер ответа;
- проверяет TLS и поддерживает certificate pinning;
- не журналирует тела `/v1/config`, потому что документ содержит RCON password;
- по умолчанию запрещает `http://`;
- использует revision/`If-Match` при изменении конфигурации;
- меняет только `DefaultReservedPlayerIds`, сохраняя остальные строки документа.
- последовательно выполняет все изменения Reserved slots, чтобы конкурирующие VIP, недельная награда и административная защита не перезаписали друг друга в случайном порядке.

При `http://` Bearer-пароль идёт по сети без TLS. Allowlist источника резко уменьшает поверхность атаки, но не шифрует трафик от перехвата на маршруте. Максимальная защита требует HTTPS/private network со стороны провайдера или доверенного прокси в защищённом сегменте.

Для текущей установки указаны два прямых WDRCON-адреса: `http://51.83.166.12:7799` и `http://216.144.249.92:7789`. Проверьте внешний port mapping в Qonzer. `http://rcon.wardogs.com` на стандартном порту является HTML-консолью и не принимается как API endpoint. Для HTTP требуется явный `RCON_ALLOW_INSECURE_HTTP=true`. Ограничьте доступ к обоим RCON по исходящему IP BotHost; предпочтителен доверенный HTTPS-прокси с `RCON_ALLOW_INSECURE_HTTP=false`.

## Discord

- Используется отдельное приложение и токен.
- Нет Message Content intent и полного Guild Members intent.
- Бот читает voice state нужного сервера и события создания сообщений в одном канале инструкций, но без Message Content intent не получает и не обрабатывает их текст. Сторонние сообщения там удаляются по ID.
- Ответы о балансе, привязке и покупках ephemeral.
- Список сидеров доступен только через ephemeral-ответ административной команды и показывает SteamID лишь по последним четырём цифрам.
- Упоминания по умолчанию отключены; при создании сбора разрешено уведомление только выбранной роли участников.
- Админ-команды требуют Manage Server **и** разрешённую роль.
- Для этой установки разрешённые роли: `805429609457254450` и `815605974412558376`; бот работает только в guild `403186008579112973`.
- Роль `859738052666327040` отдельно допускается только к `/seed-gather start/status/stop` без Manage Server. Она не включается в список полных администраторов. Все обращения к `/seed-admin` сохраняют прежнюю двойную проверку; неизвестные действия через `/seed-gather` отклоняются до вызова сервисов.
- Покупка идемпотентна по Discord interaction ID.
- Команды имеют локальный rate limit.
- Код привязки живёт 5 минут, хранится как HMAC и блокируется после 5 ошибок.
- Отвязка освобождает активные blind indexes, завершает текущую сессию и оставляет зашифрованную архивную запись с HMAC-аудитом. Баллы не удаляются и не могут автоматически перейти на другую пару Discord↔Steam.
- Отвязка блокируется, пока VIP активен либо ожидает добавления/удаления, чтобы не оставить бесхозный reserved slot.
- Управление ролями ограничено тремя закреплёнными ID. При старте проверяются Manage Roles, существование ролей и их положение ниже роли бота. Неудачные операции помещаются в зашифрованную идемпотентную очередь.
- В канале инструкций требуется только Manage Messages; содержимое удаляемых сообщений не журналируется, что исключает утечку пользовательского текста через логи.
- ID постоянных сообщений магазина, двух карточек рейтинга и правил хранятся зашифрованно. При обновлении редактируется прежнее сообщение; новое создаётся только если Discord подтвердил, что старое удалено.

## VIP и ручные reserved slots

Перед первой автоматической записью бот проверяет live- и config-списки. Если SteamID уже был зарезервирован вручную, бот помечает слот как чужой и не удаляет его после окончания купленного VIP. В сомнительной ситуации предпочтение отдаётся сохранению слота, а не удалению чужой настройки.

Для второго сервера владение ботом и состояние применения записываются в отдельный зашифрованный реестр. При пересечении оплаченного VIP, VIP за баллы и недельной награды слот сохраняется до окончания всех оснований. При недоступности журнала оплат удаление откладывается.

Reserved slot недельного победителя учитывается отдельно от покупного VIP. Если обе причины действуют одновременно, слот сохраняется до завершения обеих. Перед удалением наградного слота бот проверяет состояние VIP; при недоступном RCON операция остаётся в зашифрованной очереди. Владение слотом записывается до внешнего изменения, поэтому аварийная остановка не оставляет созданный ботом слот без учёта.

Постоянные Reserved slots находятся в отдельном AES-256-GCM-зашифрованном состоянии. Команда защиты сначала сохраняет запись и аудит, затем ставит идемпотентное добавление слота в последовательную RCON-очередь. VIP и недельная очистка проверяют реестр повторно непосредственно перед удалением. Снятие защиты не удаляет слот: это отдельное действие администратора. Такой порядок выбран в пользу сохранения доступа при любой неоднозначности.

## BotHost, Node.js и контейнер

- Основа 1.5.1 рассчитана на штатный Node.js 20.20.2 BotHost; сборка 1.7.3 сохраняет тот же диапазон Node.js 20.18–24 и закреплённые зависимости.
- Встроенный `node:sqlite`, отсутствующий в Node.js 20, заменён на точно закреплённый `better-sqlite3` 12.6.2; целостность его пакета фиксируется `package-lock.json`.
- Нативный SQLite-драйвер должен устанавливаться на BotHost во время полного деплоя. Готовый `node_modules` с другого компьютера в архив не входит.
- Собственный Dockerfile остаётся резервным вариантом для платформ, которые действительно его применяют; на текущем BotHost он не обязателен.
- При использовании резервного Dockerfile root нужен только короткому entrypoint для создания и коррекции прав `/app/data`; основной процесс запускается непривилегированным пользователем `node` через `gosu`.
- В резервном Dockerfile код приложения расположен в `/opt/wardogs-seeding-bot`, принадлежит root и недоступен процессу для записи.
- В резервном Dockerfile запись рабочих данных разрешена только в постоянный каталог `/app/data`; entrypoint отклоняет другой `DATA_DIR` и `BACKUP_DIR` вне `/app/data`.
- База и бэкапы создаются с минимальными файловыми правами и `umask 077`.
- Одновременный запуск двух экземпляров блокирует database lease.
- При обновлении ZIP BotHost должен сохранять `/app/data`; это необходимо проверить выбранным тарифом до запуска.

BotHost получает токен из поля Discord-бота как `DISCORD_BOT_TOKEN`. Код принимает это имя напрямую и отклоняет конфликтующее значение `DISCORD_TOKEN`, чтобы случайно не запустить приложение с другим токеном.

## Резервные копии

- SQLite snapshot шифруется AES-256-GCM до записи на диск.
- Временная незашифрованная копия файла не создаётся: используется in-memory serialization.
- Имя бэкапа не содержит ID участников.
- По умолчанию бэкап отправляется только в `1552401803184701502`, а digest — только в `1552402077068820611`; оба канала должны быть скрыты от `@everyone`.
- Восстановление работает только отдельной CLI-командой, не через Discord.
- Скрипт отказывается перезаписывать существующий target и выполняет SQLite integrity check.

## Реакция на утечку

### Discord token

1. Немедленно **Reset Token** в Developer Portal.
2. Заменить токен в настройках бота BotHost или переменную `DISCORD_BOT_TOKEN`.
3. Выполнить новый деплой/перезапуск бота.
4. Проверить Discord audit log и административный журнал бота.

### RCON password

1. Остановить бота или закрыть порт firewall.
2. Сменить `Password=` в Qonzer.
3. Полностью перезапустить игровой сервер.
4. Заменить secret и восстановить allowlist.
5. Проверить WDRCON audit log, если сборка его предоставляет.

### DATA_ENCRYPTION_KEY

1. Считать все идентификаторы и балансы потенциально раскрытыми.
2. Остановить бота и сохранить forensic-копию БД/логов.
3. Создать новый ключ и новую БД.
4. Перенести данные контролируемым offline-скриптом; простая смена переменной сделает старую БД нечитаемой.
5. Перепривязать пользователей, если достоверность данных под вопросом.

### BACKUP_ENCRYPTION_KEY

1. Создать новый ключ.
2. Создать свежий бэкап новым ключом.
3. Удалить старые remote-копии после подтверждённой миграции и согласно политике хранения.

## Регулярный чек-лист

- Ежемесячно: `npm audit --omit=dev`, обновление Node.js и зависимостей после тестов. Когда BotHost предложит актуальный LTS 22/24, нужно перейти на него отдельным проверенным релизом.
- Еженедельно: `/seed-admin health`, проверка приватности backup/audit channels.
- После изменения ролей: убедиться, что `/seed-admin` доступен только нужным людям.
- После смены IP бота: обновить allowlist Qonzer до запуска.
- Раз в квартал: тестовое восстановление `.wdsbak` на отдельном offline-хосте.
- После любого скриншота панели: убедиться, что токены/пароли полностью скрыты; при сомнении выполнить ротацию.
