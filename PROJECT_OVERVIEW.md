# Техническое описание RCON Panel RUBEZH

## 1. Назначение

Проект объединяет публичный сайт игрового сообщества и закрытую административную панель. Публичная часть показывает безопасную оперативную информацию о серверах. Административная часть проксирует разрешённые операции в HTTP RCON API и ограничивает их согласно ролям пользователя в Discord.

Проект рассчитан на несколько игровых серверов. Каждый сервер имеет собственный адрес, RCON-порт, токен, таймаут и необязательную ссылку подключения.

## 2. Технологический стек

### Backend

- Python 3.11+;
- FastAPI — HTTP API и маршрутизация страниц;
- Uvicorn — ASGI-сервер;
- aiohttp — асинхронное взаимодействие с RCON, Steam и Discord;
- asyncpg — асинхронная работа с PostgreSQL; aiosqlite остаётся локальным fallback для разработки;
- SQLite — пользователи, сессии, привязки ролей и накопленная статистика.

### Frontend

- Vue 3 локально в `static/vendor`, без обязательной сборки Node.js;
- обычные HTML, CSS и JavaScript;
- единый адаптивный визуальный стиль;
- периодическое фоновое обновление мониторинга.
- карточки игроков с live-действиями и переходом в Steam;
- постоянные заметки, цветные административные метки и клановая принадлежность игроков;
- срочные VIP-права, синхронизируемые с резервными игроками конкретного сервера;
- внутренние тикеты команды с обсуждением, исполнителем, статусом и приоритетом;
- управляемые временные баны с фоновым автоматическим снятием и сверкой живого бан-листа;
- поиск, сортировка и пагинация больших списков игроков и банов;
- агрегированный рейтинг игроков с поиском и сортировкой по K/D, убийствам, игровому времени, сессиям и последней активности;
- редакторы ротации и Discord-прав с черновиками, шаблонами и явным сохранением;
- собственные модальные подтверждения для опасных действий вместо браузерных окон.

### Интеграции

- WARDOGS/Dark HTTP RCON API;
- Steam OpenID и необязательный Steam Web API;
- Discord OAuth2 и Discord Bot API;

## 3. Структура проекта

```text
app/
  api.py          REST API, авторизация, разрешения и RCON-прокси
  config.py       загрузка .env и списка серверов
  db.py           схема SQLite и операции с данными
  discord.py      Discord OAuth, роли и права
  main.py         создание FastAPI-приложения и маршруты страниц
  rcon_client.py  асинхронный клиент HTTP RCON
  steam.py        Steam OpenID и профили
static/
  index.html      публичный мониторинг
  panel.html      административная панель
  app.js          общая Vue-логика мониторинга и панели
  style.css       стили сайта и панели
  calc.*          калькулятор
  stats.html      статистика
  activity.html   активность
  portal.js       общая логика дополнительных страниц
```

Локальные `.env`, `servers.json` и `site.db` не должны передаваться третьим лицам и не входят в Git/архив.

## 4. Архитектура и поток данных

```text
Браузер → FastAPI → проверка сессии и разрешений → HTTP RCON → игровой сервер
                  ↘ SQLite
                  ↘ Steam / Discord API
```

Браузер никогда не получает RCON-пароль. Backend хранит его в переменной окружения или локальном `servers.json` и сам подписывает запросы заголовком Bearer.

Для короткоживущих данных применяется кэш. Это снижает частоту запросов к игровым серверам. Для сетевых соединений используется принудительное закрытие keep-alive, поскольку игровая реализация RCON может некорректно переиспользовать соединения.

## 5. Публичный доступ

Пользователь без ролей может открыть мониторинг и увидеть:

- доступность серверов;
- текущее и максимальное количество игроков;
- карту, игровой режим и освещение;
- длительность текущего матча;
- счёт фракций;
- UUID игрового сервера.

Публично не показываются:

- список и SteamID игроков;
- полная ротация карт;
- RCON-токены и пароли;
- административные действия;
- аудит и конфигурация.

Backend также скрывает персональный список игроков и ротацию в анонимном JSON, поэтому ограничение не зависит только от интерфейса.
Анонимному посетителю доступно только число банов; полный бан-лист и каталог карт
возвращаются только пользователю с соответствующим Discord-правом.

## 6. Авторизация и роли

Основной поток:

1. Пользователь входит через Steam OpenID.
2. При необходимости привязывает Discord через OAuth2.
3. Backend получает Discord-роли участника гильдии.
4. Роли сопоставляются с набором разрешений панели.
5. Каждый административный маршрут повторно проверяет требуемое разрешение.

Поддерживаются отдельные права на просмотр игроков, приватные заметки, метки, кланы, сообщения, кик, убийство, перевод между фракциями, баны, резервные и VIP-слоты, изменение карты/света, управление матчем, аудит, конфигурацию и роли.

`WARDOGS_DEV_AUTH=1` создаёт локальный тестовый вход и разрешён только на loopback-адресе. На публичном сервере этот режим должен быть выключен.

## 7. RCON и мониторинг

Сначала панель читает `/v1/capabilities` и сохраняет список поддерживаемых маршрутов. Это позволяет скрывать или корректно обрабатывать неподдерживаемые функции.

Используемые категории RCON:

- статус и здоровье сервера;
- игроки и действия над игроком;
- баны;
- резервные игроки;
- карты, освещение и ротация;
- управление матчем;
- объявления;
- аудит;
- чтение, проверка и запись конфигурации;
- получение `/v1/server-id`.

Недоступность одного дополнительного маршрута не должна ломать всю карточку сервера. Основная ошибка статуса показывается отдельно, а вторичные данные загружаются по возможности.

## 8. Резервные слоты

Резерв разделён на две сущности:

- `MaxReservedSlots` — количество мест, удерживаемых для привилегированных игроков;
- `DefaultReservedPlayerIds` — SteamID64 игроков, имеющих право использовать резерв.

Количество резервных мест меняется через живую запись конфигурации и не требует перезапуска. Для списка SteamID панель сначала использует прямые `POST/DELETE /v1/reserved-slots`, если они объявлены сервером. Если их нет, применяется совместимый с Dark Console fallback через `GET/PUT /v1/config`.

При записи используется ревизия `If-Match`, чтобы не затереть параллельные изменения конфигурации. SteamID проверяется на формат из 17 цифр. Повторное добавление и снятие отсутствующего ID являются безопасными идемпотентными операциями.

## 9. Конфигурация

### `.env`

Основные параметры:

- `WARDOGS_PUBLIC_URL`, `WARDOGS_HOST`, `WARDOGS_PORT`;
- `WARDOGS_DB`;
- `STEAM_API_KEY`;
- `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`;
- `DISCORD_BOT_TOKEN`, `WARDOGS_GUILD_ID`;
- `WARDOGS_ADMIN_ROLES`;
- `RCON_TOKEN_<SERVER_ID>`.

### `servers.json`

Для каждого сервера указываются:

- локальный ID панели;
- отображаемое имя;
- схема, адрес и порт RCON;
- таймаут;
- необязательная ссылка подключения.

Рекомендуется оставлять поле `token` пустым и хранить секрет в `.env`.

- pytest-проверки миграции, аудита и security middleware.

### Статус масштабирования PostgreSQL

Production-режим работает через `WARDOGS_DATABASE_URL` и PostgreSQL. SQLite оставлен
для локальной разработки и обратной совместимости. Существующую базу можно перенести
скриптом `deploy/migrate-sqlite-to-postgres.py`; перед переключением нужно проверить
количества строк и `/api/ready`. PostgreSQL нужен для нескольких экземпляров приложения
и общего хранилища сессий. Для каждой будущей миграции нужно поддерживать два SQL-файла:
в `migrations/` для SQLite и в `migrations/postgres/` для PostgreSQL с одинаковым номером.

## 11. Известные ограничения

- Доступность функций зависит от версии и списка capabilities конкретного RCON.
- Сервер без корректного RCON-пароля отвечает `401` и не отдаёт ID или мониторинг.
- Тесты покрывают базовую миграцию, аудит и security middleware; покрытие RCON-моков следует расширить.
- SQLite подходит для одного экземпляра приложения; горизонтальное масштабирование потребует внешней базы и общего хранилища сессий.
- Изменения Discord-ролей кэшируются на ограниченное время.
- Высокодетальная карта калькулятора хранится во внешнем asset-хранилище и выдаётся только через allowlist-прокси; для полного автономного offline-релиза нужно отдельно перенести tile pyramid в S3/MinIO или локальное хранилище.
- Vue-шаблоны мониторинга и панели заранее компилируются скриптом
  `tools/build-vue-render.mjs`; браузер получает статические render-функции,
  поэтому CSP не разрешает `unsafe-eval`.

## 12. Безопасное развёртывание

Рекомендуемый порядок:

1. Создать отдельного системного пользователя приложения.
2. Установить зависимости в виртуальное окружение.
3. Заполнить `.env` и `servers.json` вне публичной директории.
4. Отключить `WARDOGS_DEV_AUTH`.
5. Запустить Uvicorn/Gunicorn только на localhost или внутреннем интерфейсе.
6. Поставить перед приложением Nginx/Caddy с HTTPS.
7. Ограничить сетевой доступ к RCON-портам.
8. Регулярно резервировать `site.db`.
9. Периодически менять Discord, Steam и RCON-секреты.
10. Не публиковать диагностические ответы с токенами и конфигурацией.

## 13. Проверка перед релизом

- `node --check static/app.js`;
- запуск `/api/health`;
- проверка публичной страницы без сессии;

- проверка адаптивности;
- контроль отсутствия `.env`, `servers.json`, `site.db` и секретов в архиве.

## 15. Обновление проекта

Перед обновлением сохраните `.env`, `servers.json` и резервную копию `site.db`. После получения новой версии обновите зависимости, выполните проверки и перезапустите процесс приложения. Никогда не заменяйте локальные секреты файлами из архива.

## 16. Состав финального архива

Архив содержит исходный код, документацию, шаблоны конфигурации и список зависимостей. Он не содержит Git-историю, виртуальное окружение, кэши Python, реальные токены, реальные серверные настройки или рабочую базу данных.
